# 龙游长安 · 重建计划与进度

目标、边界与做法的唯一权威记录。每个里程碑完成后更新本文件。

## 目标

架空盛唐 + 仙侠奇幻风格的 3D 自由探索页游，在浏览器运行，最终由 ChatGPT Sites 托管。

- 小龙可步行 / 骑行 / 飞行，能到各处，能贴近细看
- 宏大壮阔的建筑奇观与精致小巧的市井街巷并存
- 建模全部自建或取自免费/开源可商用素材，不使用付费资源
- 运行时共享复用材质与几何，不为每件模型重复打包
- 只保留主体玩法，不堆砌与探索赏景无关的系统
- 先做到一条街的精细度并通过用户认可，再推广全城

## 决策（已与用户确认）

| 项 | 决定 |
|---|---|
| 引擎 | 保留 Three.js，不换引擎；把建模移出运行时 |
| 建模方式 | 自建参数化构件库（Blender），辅以免费 CC0 资产 |
| 素材 | 只用免费/开源可商用；保留许可与来源 |
| 材质 | 一套共享 PBR 材质按语义复用，构件不各带贴图 |
| 功能 | 删除全部无关系统模块，只留探索/移动/镜头/赏景 |
| 分支 | `main` 为唯一权威，允许重建历史 |
| 验收 | 本地 Playwright 固定机位截图；GitHub Actions 不逐次运行 |

### 同轮：远山尝试失败并回退（建筑第二十五轮）

- **先纠正一处自己的说法**：我之前说"天空是均匀浅米色"不准确。

- 目标：在雾的可见区间内补一圈远山轮廓。**两次尝试都失败，已回退**：
  1. 一排锥体：读成纸板剪影、整齐锯齿，而且压住建筑。
  2. 连续山脊条带：半径 96m 的实体条带在俯瞰里横穿街道，

### 同轮：构件微倒角（第四十四轮）

- 画面"像 CG"的另一个根因是**几何全硬边**：构件库的 `box()` 用纯立方体，
  四角是 90° 硬切线，实时渲染下只出一条锐利切线，读作建模预览。
  真实木石构件都有 1-3mm 圆角，会在棱上接住一条细高光，
  这正是电影画面里木石"有厚度"的原因。
- 改法：在 `box()` 里给所有棱边加 `bmesh.ops.bevel`，
  倒角量按构件最小边长取 6%、夹在 2-12mm：
  太小看不见，太大会把细棂条削圆，反而不像木构。
  用 `try/except TypeError` 兼容不同 Blender 版本的参数名差异。
- 几何增量：常铺 7180 → 12744 三角形（几乎翻倍），
  酒肆 29628、三层楼 13820。整帧 374 万 → 399 万三角形。
- 效果：近景木柱与横梁的棱边不再是硬切线，而是有细高光的过渡。
- 复审 1280×720 / 844×390 均 passed，4043/4113 calls、约 399/411 万三角形。

### 同轮：地面接触阴影（第四十五轮）

### 同轮：环境贴图改用实际天空（第五十四轮）

- 发现一个隐藏很深的错误：`scene.environment` 用的是
  `RoomEnvironment`——一个**室内房间**的 HDR 环境。
  它的高光与间接光方向与户外街景完全无关，
  结果所有 PBR 材质（瓦、石、木、铁）的反射都指向错误方向，
  高光位置"对不上太阳"。这是画面像 CG 预览而缺少真实感的一个根因。
- 改法：用 `sky`（已在 `createSky` 里建好的天空球）生成 PMREM。
  只把天空球放进临时场景再烘，避免把建筑也烘进环境贴图。
  调用顺序已核实：`createSky()` 在 `createLights()` 之前。
- 效果：材质的间接光与高光方向与太阳一致，木柱、石面、铁件的反射不再
  来自室内环境，整幅画面更统一。
- 复审 1280×720 / 844×390 均 passed，4398/4468 calls、约 464/480 万三角形。

### 同轮：阴影分辨率与类型（第五十五轮）

- 继续找结构性错误。量化结果：2048 阴影贴图覆盖 104 x 112m，
  **每像素约 5cm**；街上檐柱直径只有 13cm，阴影边缘只剩 2-3 像素，必然糊。
- 第一步：贴图提到 **4096**，并把阴影相机从 ±52/±56 收紧到 **±30/±46**
  （街道两侧铺面 |x| < 22、两座门楼、殿堂），每像素降到约 1.5cm。
  bias 随分辨率提高而收紧（-0.00045 → -0.00022，normalBias 0.035 → 0.018），
  否则薄构件会漏光。
- 第二步：分辨率提高后 PCFSoft 的软化半径相对像素变小，边缘出现**阶梯**。
  改用 **VSMShadowMap**：它按距离自动软化，近处边缘紧、远处边缘柔，
  正适合 70m 长的街景。配 blurSamples 12、radius 2.2。
- 效果：人物与桌凳的落影边缘连续，不再糊成一片灰，也没有阶梯。
- 代价：VSM 需要额外的模糊通道，整帧三角形 464 万 → 590 万。
- 复审 1280×720 / 844×390 均 passed，4803/4873 calls。

### 同轮：朱红大漆的清漆层（第五十六轮）

- 朱红木构原先只是把木料染红、roughness 0.76，
  读作"红漆木板"而不是"大漆"。
- 大漆的关键是**清漆层**：底层哑光、表层有一层薄而光滑的透明漆，
  柱身因此出现一条窄而亮的高光。这才是国风建筑里朱红柱的观感。
- 改法：把 `redWood` 从 `MeshStandardMaterial` 换成 `MeshPhysicalMaterial`，
  保留原有的 map / normalMap / roughnessMap，
  加 `clearcoat 0.55`、`clearcoatRoughness 0.30`，
  roughness 0.76 → 0.62、normalScale 0.55（漆面比生木更平整）。
  不改几何，只改材质类型。
- 效果：朱红木柱出现窄高光，不再是一整片哑光红。
- 复审 1280×720 / 844×390 均 passed，4803/4873 calls、约 590/606 万三角形。

### 同轮：空气透视（第五十七轮）

- 上一轮量出远近铺面亮度只差 0.018（0.266 vs 0.284），
  说明雾几乎不起作用。查源码：`Fog(0xe6d5b8, 40, 168)`——
  雾从 40m 起、168m 才结束，而街长只有 72m，**雾在街内基本无效**。
- 改为 `Fog(0xe6d5b8, 18, 96)`：近端 18m 起、远端 96m 结束，
  街内 30-70m 处能看出逐层后退。
- 实测对比（同一取样点）：
  - 远处右侧铺面 0.114 → **0.197**（衰减明显加强）
  - 远处左侧铺面 0.266 → 0.258
  - 近处基本不变（0.284 / 0.351）
- 效果：街道尽头的塔与门楼明显退入空气，纵深层次拉开。

- 复审 1280×720 / 844×390 均 passed，4803/4873 calls。

### 同轮：太阳高度角与雾的联动（第五十八轮）

### 同轮：指数雾替代线性雾（第五十九轮）

- 上一轮暴露出线性雾的**结构性矛盾**：
  要让街内有纵深就得近端起雾，但近端起雾必然把 39m 处的坊门
  （街道尽头唯一的地标）冲成白色（实测 0.759-0.784）。
  靠调远端只是在这两者之间妥协，不可能同时满足。
- 改用 `FogExp2`（指数雾）：衰减是"先缓后急"，
  正好同时满足两个要求——街内 10-40m 衰减很轻（地标保住），
  50m 之后迅速加深（纵深成立）。这也更接近真实的空气散射。
  density 0.0092：40m 处约衰减 13%，70m 处约衰减 34%。
- 实测对比：
  - 坊门亮度 0.639 → **0.589**（比线性雾更低，但轮廓更清楚）
  - 中景铺面暗部 0.219（保住，没有被雾洗白）
  - 远景地面 0.583
- 复审 1280×720 / 844×390 均 passed，4937/5007 calls、约 611/627 万三角形。

### 同轮：铺面立面变化（第六十轮）

- 24 间铺面用的是同一套构件库（四档 GLB + 酒肆），
  主体立面必然相同，一条街看过去有复制感。
- 真实市街的差异来自"店家自己加的"东西——不属于营造制度，

  1. **短椽头**（variant 0）：挑檐下加一排 5 根小椽，读作"店家加的小檐"。
  2. **垂花柱**（variant 1）：檐下两根短柱 + 三层渐小的柱头雕花。
  3. **外挑雨篷**（variant 2）：小斜板 + 两根斜撑，比布篷更小更随意。
  4. **矮门楼**（variant 3）：门框 + 小额枋，读作"这家的门脸更讲究"。
- 效果：相邻铺面的立面不再雷同，街景出现"店家各自添置"的层次。
- **一个实现错误**：首次插入把函数放进了另一个函数的注释块内部，
  页面报 `addFacadeVariation is not defined` 并卡在加载。
  靠读控制台错误 + 查 `s.find()` 位置定位，改为插到顶层 `createStreet` 之前。
- 复审 1280×720 / 844×390 均 passed，5090/5162 calls、约 611/627 万三角形。

### 同轮：人物姿态差异与一次诚实的判断（第六十一轮）

- 先量化：32 个人物、**18 种朝向**，朝向分布已经比较丰富；
  人物还有 5 种服色与 0.88-1.03 的身高差异。
- 给每人加了确定性微姿态：朝向 ±0.05 rad、侧倾 ±0.045、前倾 ±0.035、
  身高再浮动 ±1.5%。幅度刻意很小——人的站姿差异本来只有几度，
  超过 3 度会读成"站不稳"。
- **诚实的判断**：这轮改动对画面的实际改善很有限。
  人物真正的重复感来自**站姿本身**（双手垂放的僵直姿势），
  而不是朝向或倾斜。人物的 GLB 是静态分件网格、**没有骨骼**，
  要改站姿必须重建模型或加骨骼绑定，属于造型级工作，
  不是这一轮能顺手做完的，也不该用微调冒充解决。
- 复审 1280×720 / 844×390 均 passed，5090/5162 calls、约 611/627 万三角形。

### 同轮：人物随身物件（第六十二轮）

- 上一轮判断人物重复感来自站姿。本轮先验证能否改站姿：
  枚举人物的 17 个分件，发现它们是**细碎部件**（眉毛、虹膜、衣缝、眼睛），
  不是"手臂 / 头 / 躯干"这类可旋转的整块，**没有骨骼也无法旋转分件**。
  这条路确认走不通，不再尝试。
- 改用另一条可行的路：给人物加**随身物件**，
  "手上有没有东西"是站姿读起来活不活的关键。
  按确定性序号分三种：提篮、横抱布卷、挑担。
- **第一版位置错误**：扁担悬在头侧、货物浮在身前，读作"飘着两个罐子"。
  按人体实际尺度重算：身高约 1.73m、肩高约 1.40m，
  扁担压肩（z 略后）、加两段吊绳垂到货物、货物挂在腰胯两侧（y 1.02）。
  提篮与布卷同样下移到胯旁与腰际、贴住身体。
- 效果：街面人物出现"挑担赶路""提篮买菜"的动作，不再是清一色垂手站立。
- 复审 1280×720 / 844×390 均 passed，5226/5299 calls、约 612/628 万三角形。

### 同轮：墙面纹理密度（建筑第七十六轮）

- 近景截图暴露出一个此前没抓到的问题：**背景铺面与墙体是纯粹的光板**，

### 同轮：构件库 UV 缺失（建筑第八十轮，本轮最重要的修正）

- 核对屋顶瓦垄时发现：`tang_kit.py` 里**从未出现 `uv_layers`**，
  整个构件库没有任何 UV 展开代码。
- 进一步读 GLB 的 TEXCOORD 数据，确认是**退化 UV**：
  绝大多数构件 `u[0.00, 0.00]`、`v[1.00, 1.00]`——
  U 方向完全不变，贴图在 U 方向被压成一个像素，
  **所有构件采样到的都是一条单像素色带**。
- 这是"建筑像纯色板"的根本原因，比之前修的所有纹理密度问题都更底层。
  换多高分辨率的贴图都没有用——采样到的本来就不是纹理。
- 修法：在 `new_object` 里加**立方投影 UV**（按面法线主轴选投影平面，
  UV 直接等于世界坐标的米数）。重导后 UV 变成真实坐标
  （如墙面 `u[-2.46, 2.46]` 对应 4.92m 宽）。
- 随之而来的语义变化：UV 单位变成米，repeat 语义从
  "整块构件铺几次"变成"每米几个周期"。为免与场景平面（0-1 UV）
  冲突，新增 `kitMaterialFor()` 派生一套**米制材质副本**
  （repeat 1,1），并在 `createStreet` 里把五个构件语义名
  （`mat_stone` / `mat_plaster` / `mat_timber` / `mat_vermilion` /
  `mat_bracket_block` / 三个 `mat_roof_*` / `mat_cloth`）
  注册进 `window.KitLibrary.materials`，覆盖默认材质。
- 复审 1280×720 / 844×390 均 passed，15 GLB 全加载 0 失败。

### 同轮：场景手建几何补齐 UV（建筑第八十一轮）

- 上一轮修好构件库的 UV 后，重看近景发现**背景墙面仍是一片纯色**。
- 定位：场景代码里手写的 `BufferGeometry` **全都没有 UV**——
  `taperedBox`（门墩、坊墙、翼墙、殿堂台基、巷墙）、
  门楼斗拱的 `loftRings` 与 `makeGong`、门楼屋面、圆弧筒瓦、塔檐。
  没有 UV 的几何采样不到贴图，表面必然是纯色。
  这与构件库的退化 UV 是**同一类问题**，只是发生在场景代码这一侧。
- 修法：逐处按构件自身切向轴生成**米制 UV**：
  - `taperedBox`：6 个面各按自己的两个切向轴（x/z、z/y、x/y）；
  - `loftRings`：侧面按周长、竖向按高度；
  - `makeGong`：按轮廓的 x/y；
  - 屋面：横向按宽度、纵向按坡长；
  - 筒瓦：沿瓦垄按坡长、横向按圆弧展开长度；
  - 塔檐：环向按周长、径向按坡长。
- 效果：墙面出现抹灰斑驳、木构出现木纹，贴图才真正作用在建筑上。
- 复审 1280×720 / 844×390 均 passed，5412/5488 calls。

### UV 问题的完整链条（两轮修完）

1. **构件库**：`tang_kit.py` 从未展开 UV，导出的是退化 UV
   （u 恒为 0），贴图被压成单像素色带。→ 加立方投影 UV。
2. **材质语义冲突**：构件用米制 UV、场景平面用 0-1 UV，
   共用材质时 repeat 语义冲突。→ 派生米制材质副本并注册进 `KitLibrary`。
3. **场景手建几何**：`BufferGeometry` 全部没有 UV。→ 逐处补米制 UV。

这三处叠加，才解释得清"为什么换了 2k 贴图、调了调色、改了光照，
建筑看起来仍然像纯色板"。

### 一条贯穿本次会话的根本教训

"贴图在正常工作"这个前提，在很长时间里是**错的**。
UV 退化 + 材质语义冲突 + 手建几何无 UV，三者叠加，
使得贴图从未真正生效。在这个错误前提下做的所有
贴图分辨率、调色、光照调整，效果都被打了折扣。
**先验证底层数据（UV、法线、贴图采样）是否正常，
再谈上层观感**——这条比任何具体修正都重要。

### 一条方法上的收获

**每一次改动底层（UV、材质语义、几何）之后，之前调好的上层参数（曝光、
光比、调色）都需要重新量一次。** 这次就是典型：
上一轮的 UV 修复让曝光重新变得不足，而我如果只看截图"感觉还行"
就会漏掉。用直方图量出来才明确。

### 一条三次验证的排查顺序

### 为什么第二次失败

只考虑了"接缝宽度"，没考虑"石板尺寸变小后，底层颜色暴露的比例变大"。
底层（`pavingBase`）是亮褐色，石板是青灰——接缝变宽时它本来是作为"缝隙"存在的，
但石板缩小后，露出面积增加，它就从"缝隙"变成了"条纹"。
**改一个参数前，要把它牵连的另一层一起算进去。**

### 同轮：铺装底层颜色（建筑第九十四轮）

  `pavingBase` 的颜色是 0x8b8377（亮褐），而石板是青灰 0xa8b0ac。
  接缝窄时它只是"缝隙"，石板一缩小、露出面积增加，它就变成"条纹"。
- 这一轮先修底层：0x8b8377 → **0x6e746f**（与石板同色系、只暗一档）。

- 效果：石板之间的接缝读作阴影，地面看起来是连续的石板路，

- 修法：`taperedBox` 里的米制材质按"贴图覆盖 2.5m"重设 repeat，
  密度降到约 820 px/m，与墙面的合理区间一致。
- 翼墙查证：材质是 `street-plaster-kit-taper`、**有贴图**，
  但仍读作平涂。原因是米制 repeat 把贴图放大后，
  单块 7.2m 宽的墙只看到约 3 个周期，斑块被放大、
  局部对比被稀释。把 canvas 斑块 alpha 从 0.16 再提到 **0.26**。
- 效果：门墩出现石纹、翼墙出现抹灰深浅层次。
- 复审 1280×720 / 844×390 均 passed，5537/5611 calls。

### 一条反复出现的规律

"贴图存在"不等于"贴图可见"。已经遇到三种情况：
1. 退化 UV（u 恒为 0）；
2. 无 UV；
3. **有 UV 有贴图，但 repeat 使密度过高或过低**。

第三种最难发现——所有检查都显示"正常"，只有量实际像素密度才看得出来。

### 同轮：叶片材质双面光照（建筑第一百轮）

- 酒肆近景暴露一处与建筑同级的问题：**前景树叶是扁平纸片状**，
  边缘锐利、背面发黑，与背景建筑的精细度形成落差。
- 查证：树已经用 lod0（最高精度，street 6806 三角形 vs lod1 2958），
  所以不是精度问题。叶片是卡片几何，这在实时渲染里是标准做法。
- 真正的缺陷在**材质**：叶片双面渲染时背面法线朝外，
  会按"背光"计算，整片叶子读作硬纸片。
- 修法：对带 alpha 的叶片材质——
  1. `side` 与 `shadowSide` 都设为 `DoubleSide`（阴影也按双面算）；
  2. `envMapIntensity` 提到 0.95，让背光面仍能接住天光；
  3. 粗糙度取 ≥0.82、金属度 0，避免出现塑料高光。
  树干（无 alpha）保持原样。
- 效果：叶片背面不再发黑，能接住天光，读作有体积的树冠。
- 复审 1280×720 / 844×390 均 passed，5537/5611 calls。

### 同轮：布料 shadowSide 同步（建筑第一百零一轮）

- 承接上一轮叶片材质的发现，核对所有双面材质。
- 数据：布料（`street-cloth` 系列）的 `side` 是 double，
  但 `shadowSide` 是 **default**（即单面）。
  双面渲染、单面投影——布篷正下方的阴影因此缺失。
- 修法：`cloth.shadowSide = THREE.DoubleSide`，与 `side` 同步。
- 效果：布篷正下方的地面明显压暗，投影与受光一致了。
- `facade-shade`（遮片）不投影，保持 default 是正确的，未改。
- 复审 1280×720 / 844×390 均 passed，5537/5611 calls。

### 双面材质的两项一致性

| 属性 | 作用 | 必须一致的原因 |
|---|---|---|
| `side` | 正面与背面是否都渲染 | 决定"看得见" |
| `shadowSide` | 投影时按单面还是双面算 | 决定"影子对不对" |

两者不一致时，物体看得见但影子缺失（或相反），
这在布篷、旗帜、叶片这类薄片上最容易出现。

### 同轮：阴影标志一致性（建筑第一百零二轮）

- 承接上一轮，核对 `castShadow` 与 `receiveShadow` 是否成对设置。
- 普查结果：4201 个网格中，**96 个"只接收不投射"**。

### 同轮：石板逐块色差（建筑第一百零五轮）

- 先核对构造：坊墙**已有石砌墙基**（0.42m 高、`stoneWithPeriod` 材质）；
  路缘石与明沟都已存在。**构造完整，不改。**
- 转而量画面：按纵向五条带比较亮度标准差——
  | 条带 | 位置 | sd |
  |---|---|---|
  | band 0 | 远景建筑 | 0.187 |
  | band 4 | **近景地面** | **0.089** |
  近景（玩家视线停留最多的地方）读作一片均匀的灰。
- 查石板：确实有逐实例颜色，但四种色 0x84806f~0x7a7768
  亮度差只有约 **4%**，肉眼看不出来。
- **三次调整**：
  1. 范围拉到 22% → **失败**，读作明暗交替的棋盘格，比原来更假；
  2. 收到 10%、改用 `(row*29+column*17)%5` 打散 → **棋盘格仍在**
     （线性组合相邻列固定差 2、相邻行固定差 4，规则感来自公式本身）；
  3. 改用异或散列 `((row*73856093)^(column*19349663))%5` → **成立**，
     不规则深浅，读作真实石路。
- 最终 sd 0.089 → **0.101**，近景亮度 0.270 → 0.309。
- 复审 1280×720 / 844×390 均 passed，5978/6052 calls。

### 从三次调整里得到的判断

色差不足 → 读作均匀；色差过大 → 读作棋盘格。
**"有变化"和"有节奏"是两件事**：真正的随机石路既要有差异，
又不能有可辨认的规律。线性公式无论怎么调参都带规律，
必须换成散列。

### 同轮：散列再混一层（建筑第一百零六轮）

- 上一轮的散列 `((row*73856093)^(column*19349663))%5` 仍有**横向条带**：
  两个大质数与 5 的关系让 row 的变化在模 5 上接近等差。
- 改为两步混合：
  1. 先把 row / column 各自乘大质数后异或；
  2. 再与自身右移 13 位的结果异或、乘 1274126177；
  3. 最后取高位（`>>> 3`）再模 5。
  这样低位也被高位影响，行/列方向的节奏才真正消失。
- 效果：横向条带消失，石板呈不规则深浅。
  band 4（近景地面）sd 保持 0.101。
- 复审 1280×720 / 844×390 均 passed，5978/6052 calls。

### 关于"随机"的一条判断

这一处连续四轮才做到位：
4%（看不出）→ 22%（棋盘格）→ 线性打散（斜纹）→
异或（横条）→ **两步混合（成立）**。

**凡是要"看起来随机"的地方，都不能用线性公式**；
必须先混合高位与低位，再取模。

### 同轮：地面亮色方块的三项修正（建筑第一百零七轮）

### 同轮：测量工具的可复现性（建筑第一百零八轮）

上一轮因"两次截图视角不同"白走了六轮，本轮先修工具。

- **`capture.py` 的 `near` / `side` 视角**没有设定 `position`，
  依赖上一视角的残留状态——同一视角在不同调用顺序下拍出不同画面。
  已补齐完整相机状态。
- 但补齐后仍不稳定（near mean_diff 32.7、side 38.6）：
  原因是这两个视角 `near = true`，相机**跟随龙头**，
  而龙有呼吸与姿态动画。这是设计如此，不是缺陷。
- 新增 `fixed_capture.py`：把龙的位置、朝向、距离、环绕角全部钉死，
  相机每次算出完全相同的结果。实测两次独立运行：
  ```
  camPos [-0.0, 3.199, 30.238]  camRot [-0.2515, -0.0, -0.0]
  ```
  完全一致；像素差异 mean_diff 1.78（来自灯笼与行人的动画，
  不是相机漂移）。

**结论：A/B 测量必须用 `fixed_capture.py`；
`capture.py` 用于观感评估，不能用于数值对比。**

### 同轮：墙面 repeat 与 UV 单位不符（建筑第一百零九轮）

- 先核实人物本身：36 个人形组、身高中位数 **1.74m**、
  范围 1.34-1.94m——**比例正确，不需要改**。
- 但量分布发现：站在地面的只有 **22 人**，沿 72m 的街中位间距 **2.5m**，
  读作"空旷"而不是市集。手工清单是硬编码的 26 个位置，
  无法按需增加。
- 修法：在清单后追加 **18 个程序化生成的行人**——
  z 在 -34~28 均匀铺开、两侧交替、靠边站（距街心 3.4-4.6m，
  避开摊位与门槛），朝向街心。用固定散列（两步混合）保证
  每次加载的街景一致，而不是随机漂移。
- 实测：落地人数 22 → **36**，中位间距 2.5m → **1.5m**。
  街上明显热闹，街心仍保留龙的通行空间。

## 决策记录

- 构件几何统一以"底面 z=0"为基准，便于按层堆叠与复用。
- 尺寸一律以"分"为单位建模、按材等换算成米，一等材 30cm 用于殿宇，
  三号材 22cm 用于市井，构件代码完全共用。
- 舍去明清琴面昂/象鼻昂，下昂用唐式批竹昂（直斜面、昂嘴平切）。
- 斗拱按"沿墙梯 + 出跳梯两条独立叠置"实现，共用栌斗并十字相交，
  这正是栌斗要开十字口的结构原因。
