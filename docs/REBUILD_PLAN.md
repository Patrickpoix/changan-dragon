# 龙游长安 · 重建计划与进度

目标、边界与做法的唯一权威记录。每个里程碑完成后更新本文件。

## 目标

架空盛唐 + 仙侠奇幻风格的 3D 自由探索页游，在浏览器运行，最终由 ChatGPT Sites 托管。

- 小龙可步行 / 骑行 / 飞行，能到各处，能贴近细看
- 宏大壮阔的建筑奇观与精致小巧的市井街巷并存
- 建模全部自建或取自免费/开源可商用素材，不使用付费资源
- 运行时共享复用材质与几何，不为每件模型重复打包
- 只保留主体玩法，不堆砌与探索赏景无关的系统
- 先做到一条街的精细度并通过用户认可，再推广全城

## 决策（已与用户确认）

| 项 | 决定 |
|---|---|
| 引擎 | 保留 Three.js，不换引擎；把建模移出运行时 |
| 建模方式 | 自建参数化构件库（Blender），辅以免费 CC0 资产 |
| 素材 | 只用免费/开源可商用；保留许可与来源 |
| 材质 | 一套共享 PBR 材质按语义复用，构件不各带贴图 |
| 功能 | 删除全部无关系统模块，只留探索/移动/镜头/赏景 |
| 分支 | `main` 为唯一权威，允许重建历史 |
| 验收 | 本地 Playwright 固定机位截图；GitHub Actions 不逐次运行 |

### 同轮：远山尝试失败并回退（建筑第二十五轮）

- **先纠正一处自己的说法**：我之前说"天空是均匀浅米色"不准确。

- 目标：在雾的可见区间内补一圈远山轮廓。**两次尝试都失败，已回退**：
  1. 一排锥体：读成纸板剪影、整齐锯齿，而且压住建筑。
  2. 连续山脊条带：半径 96m 的实体条带在俯瞰里横穿街道，

  重拍一次即正常——判断回归前要先排除缓存。

### 同轮：远山改为天空着色（建筑第二十六轮，成功）

- 上一轮两次实体几何方案都失败并回退。本轮改为**在天空 shader 里画山脊**：
  按视线方位角算出两层山脊高度，视线低于山脊就混成山色。
  纯着色、不参与深度、不可能遮挡建筑，这是这次做成的关键。
- 调参过程全部靠像素测量，不靠肉眼判断：
  1. 初版 0.030 rad（约 1.7°）——用诊断着色确认 mask 数学正确，
     但高度太低，被街两侧建筑完全挡住，肉眼看不出。
  2. 抬到 0.105-0.150 rad——像素测量显示天空带明度跨度 85-127，
     说明山确实在渲染，但仍只占最下面一条。
  3. 抬到 0.160-0.225 rad + 加深山色（近层 0.14/0.17/0.19、
     远层 0.30/0.33/0.35）——街尽头门楼后方出现两层山脊，
     近层深青灰、远层淡青，天际线不再是一条平直的米色带。
- **诊断方法记录**：把 sky 的 fragmentShader 临时替换成
  "低于山脊涂红、高于涂绿"，直接看 mask 是否生效——
  比反复调参猜参数快得多。
- 复审 1280×720 / 844×390 均 passed，3876/3906 calls、约 335/339 万三角形；
  基座重叠 0，24 间全部测到。

### 同轮：深红方块缺陷已修复（建筑第二十七轮）

- **根因终于定位**：那两块深红方块不是门楼的构件，而是**殿堂台基的下沿压边石**。
  `addWardHalls` 里用 `materials.darkWood`（#b08a72，偏红褐）做了一块
  `16.8 x 0.5 x 12.4` 的台基压边，它比台基宽 0.2m，
  从门洞看过去正好在坊门两侧墙脚各露出一角，读成两块突兀的深红方块。
- **决定性的一步**：把 `ward-halls` 整组隐藏后红方块消失，门洞只剩米色坊墙。
  这一步只花了一次截图，比前六种方法加起来都有效——
  之前一直假设红方块属于门楼，方向就错了。
- 修法：压边石改用 `materials.stone`（台基下沿本来就该是石色）。
- **同时清理**：上一轮为"盖住"红方块加的两块压边石没有起作用，
  且注释写着"遮住了"与事实不符。已删除那两块，并修正注释。
- 前六种失败的方法（射线拾取、包围盒扫描、屏幕投影、材质染色、
  枚举低矮网格、精确像素射线）之所以都失败，共同原因是
  **它们只在门楼附近找，而红方块在 13m 外的殿堂台基上**。

### 同轮：灯笼重做（建筑第二十八轮）

### 同轮：街树改用 lod0（建筑第二十九轮）

### 同轮：贴地核查与摊位桌腿（建筑第三十轮）

- **先撤回两条自己的错误判断**（都是凭印象下的结论）：
  1. "水缸落地位置随意"——实测 24 个罐子里 20 个底部在 y=0.89
     （放在摊位桌面上，桌高 0.89m，合理），4 个地面罐底部在 0.05，
     而铺装顶面是 0.043-0.048，正好落在铺装面上。贴地是正确的。
  2. "右侧木柱过粗"（上一轮已撤回）——柱身半径 0.065m，属透视放大。
- **改成先量化再动手**后，反而找到一处真实缺陷：
  摊位桌面的中心 0.82、厚 0.09（底面 0.775），桌腿高 0.78、中心 0.4
  （顶端 0.79）——桌面浮在桌腿上方 0.035m 的空隙里，尺寸根本对不上。
  改为由桌面位置反推腿高，让腿顶正好顶到桌面底面、腿底落在铺装面上。
- 复核方法：统计"直接挂在场景上的独立物件"的 minY 与铺装顶面的差，
  而不是统计所有网格（后者 603 个"悬空"里绝大多数是物体的组成部分，
  如石狮的腿与鬃，统计方式本身是错的）。
- 复审 1280×720 / 844×390 均 passed，3976/4006 calls、约 347/351 万三角形。

### 同轮：门洞铺装补全（建筑第三十一轮）

- **先记录一次失败的排查**：为找"构件之间没接上"的缺陷，我连续三次
  写错了检测脚本——`includes('--1')` 把 z 的负号误判成 side、
  按 `-` 切分组名解析失败、最后改用 `group.userData.entry.side` 才正确。
  正确的结论是：左右各 12 间、檐口间隙全部 -0.12m，**没有任何重叠**。
  三次同类失败说明"猜缺陷"这条路不划算，改为直接看画面。
- **看画面才找到的真问题**：门洞后方（更远那一侧）是裸露的
  `far-ground` 米褐色大平面，与灰色铺装形成一条硬切的边。
  原因是门洞铺装只有 12m 长（只覆盖门洞前 6m）。
- 修法：门洞铺装延长到 20m 并整体后移，石板行数 12 → 22，把门洞内外都铺到；
  同时把 `nearGround` 土路从 40×90（z 从 -48 到 +42）收到街段长度，
  不再整片压住门洞铺装。
- 修后门洞区域地面连续，褐色土面消失。
- 复审 1280×720 / 844×390 均 passed，3976/4006 calls、约 347/351 万三角形。

## 决策记录

- 构件几何统一以"底面 z=0"为基准，便于按层堆叠与复用。
- 尺寸一律以"分"为单位建模、按材等换算成米，一等材 30cm 用于殿宇，
  三号材 22cm 用于市井，构件代码完全共用。
- 舍去明清琴面昂/象鼻昂，下昂用唐式批竹昂（直斜面、昂嘴平切）。
- 斗拱按"沿墙梯 + 出跳梯两条独立叠置"实现，共用栌斗并十字相交，
  这正是栌斗要开十字口的结构原因。
