# 龙游长安：产品目标、制作方法与验收标准

这份文档保存用户跨会话不变的要求。新会话先读本文，再读 [CONTINUE.md](CONTINUE.md) 获取实际进度。本文不是“已经完成”的声明；当前程序可玩，整体美术仍与认可参考有明显差距。用户后续明确的新要求优先于本文，修改时同步更新相关约定。

## 1. 要做成什么

**2026-10-23人物纠正，优先于早期“卡通人物/夸张头身”建议：** 唐人保持正常人的人体与脸部结构，与现代人无本质区别；时代感主要来自发式、服饰、妆容、身份装束。禁止为“国漫”放大头眼、缩短肢体、夸张颌骨或将脸部做成非人形。自然个体差异与表情保留，电影感依赖造型完成度、材质、光影和动作。Snow/Rain夸张人物试片已否决作本项目造型基准，不因模型成熟就直接套用。

2026-10-23再次确认：追求《长安三万里》《大理寺日志》那样的电影国风和类似3A游戏的沉浸式质感与可信感，**不是简单卡通化**。小龙的可爱与城市/人物/材质的细腻并存。用户补回的人物、完整店铺与材质研究原件见 [旧会话参考归档](user-references/2026-10-23/README.md)，必须参与后续造型验收。

让一只可爱、圆润、有表情的小青龙，在唐代长安城中自由赏玩。目标是具有国漫电影场景、画风、光照和材质观感的沉浸式三维城市：宏伟建筑与有生活气息的近景同样重要。用户以“3A大作”表达质量期待，不能用“浏览器项目”作为简陋的理由，也不能把这个期待冒充已经实现的技术或商业等级。

骑木制自行车只是游览方式之一。必须同时支持步行、骑行、飞行、自由探索、多视角，以及便于欣赏城市的电影镜头。没有强制骑行竞速目的；诗笺等收集应可选，不打断赏景。

主要交付是在手机浏览器可运行的游戏，横屏优先。语言和格式由开发者根据目标选择；项目现用静态HTML/JavaScript/Three.js，保留可下载单HTML离线版。具体手机本地打开方式受系统浏览器限制，需真实验证并如实说明。

## 2. 用户明确提出的画面与内容

| 方面 | 必须达到的行为或观感 |
| --- | --- |
| 美术 | 国漫电影般的场景质感，丰富协调的色彩、圆润饱满的体积、清晰的材质区分；不接受当前简陋原型作为终点。 |
| 小龙 | 可爱卡通龙，面部有吸引力，轮廓、眼神、表情、身体和动作统一；木自行车及骑行关系可信。 |
| 建筑 | 宏伟、立体，可从多个角度观赏；唐风屋顶、木构、斗拱、门窗、台基形成尺度和层次，不能只有一排方盒。 |
| 城市 | 有真实可游走的城池、坊市、街巷与店铺，地区丰富多元，有明显的空间关系和地标。 |
| 生活 | 沿街商贾、叫卖和行人，货品、交通及游览活动；人群和铺面不能只是静止装饰数量。 |
| 水岸 | 画舫、游船、连廊、亭台楼阁与园林，水陆空间丰富，船只吃水、动作和通行可信。 |
| 探索 | 可自由到各地玩，步行/木自行车/飞行均有完整控制、合适镜头和安全的地面/水域/建筑处理。 |
| 设备 | 横屏手机可操作、内容可读、触摸控件可靠，支持多视角；桌面便于开发和游览。 |
| 可维护 | 最终场景、对象、移动、碰撞、镜头和交互均在代码/可编辑三维资产管线中实现，便于以后调整。 |

这些是内容类别和质量要求，不是规定每个坊都机械重复同一套对象。每一区应有自身构图、建筑组合、营业内容、植被与人群节奏。

## 3. 认可的美术方向与不可取代的实现要求

主参考为 [art-direction.png](art-direction.png)；分区参考为 [市集](concept-market.png)、[宫殿](concept-palace.png)、[曲江](concept-qujiang.png)。用户认可的是其审美、电影质感和城市丰富度，不代表已经接受当前代码画面。概念中的细节也不能自动变成唐代考古结论。

**用户最新补充：建筑、人物、风景的建模语言本身有问题，不能只增加精细度。** 具体指定《长安三万里》和《大理寺日志》作为详细研究对象。已核实的公开图像分析、背景区别、代码诊断与模型重做规范见 [影视风格研究](FILM_STYLE_RESEARCH.md)。先重做并验证完整模型，再扩展全城；不能继续以旧模型加密作为主要方案。

制作时具体对照：

- 暖色木构与灰青瓦顶、玉色主角、克制金色细节，主体与背景颜色有主次，不靠浓雾和泛光掩盖粗糙模型。
- 人的视角能读出石材、木头、布、陶器、水、皮肤的差异，边缘有细微圆润与真实尺度；远处仍有完整屋顶与城市轮廓。
- 前景有树枝/铺货/栏杆，中景有小龙与行人，远景有塔楼与宫城；街道有连续界面和可游览空间，避免巨大空地配零散积木。
- 门窗、檐下、摊篷和檐廊有深度、接触阴影与结构；从背面、侧面和空中看仍成立。
- 人群、舟船、树叶与角色动作营造生活感，镜头运动平稳，景观与操作不互相遮挡。

用户允许使用 image2.5 等生图能力制作概念和缺失视觉参考；已有满意参考可直接继续使用。**最终必须是真三维游戏。** 不采用概念画当作整座城市背景，不用预渲染视频、2.5D贴片或纯平面角色替代需要环视、飞越和进入的实体。生图有助于决定模型/材质/构图，不替代几何、碰撞、动作与交互实现。

## 4. 用户要求的制作循环

**用户最新明确的本阶段顺序：先把总体设计框架确定准确，逐项构思全部内容的正确形态/改法，充分联网寻找所需素材、材质包、模组、引擎与素材库，然后才开始正式整合。** 当前执行 [DESIGN_FRAMEWORK.md](DESIGN_FRAMEWORK.md) 的地区/资产合同与G0–G4关口；研究目录为 [resource-catalog.json](resource-catalog.json)。整体设计已形成，关键生产模型/可编辑源与专项设计仍有缺口，不越过准备阶段继续批量铺旧模型。这个顺序是本阶段的用户指令，不是要求反复征求常规开发批准。

持续执行“联网找素材/生成参考 → 整合 → 精修 → 再找素材/生成参考 → 再整合 → 再精修”，直到产品和视觉要求完成。不要只搜少量来源就停止，也不要把大量下载本身视作进展。

用户希望多采用审美成熟、适合需求的现成模型、材质、成品包、引擎模块、代码库和语言资源，经过统一调整后整合，减少从零手搓的低质重复劳动。具体资源可以不采用；必须说明风格、时代、许可或预算方面的理由。现有素材研究已有可用来源和被否决候选，继续之前先读，避免重复碰到登录/配额问题。

下列是实现这些要求的**工程建议**，不是用户指定的唯一技术方案：

1. **先找最大可见差距。** 运行当前版本，对照认可概念，选最能改善城市观感的模块或代表路线；不要无休止只修小技术点而不改善建筑、人物和构图。
2. **先完成代表性区域。** 先把一段繁华市街、一个宫苑视点、一处水岸做成可环视、可走入的高质量样板，再按共享模块扩展全城；始终保留三种移动方式的完整性。
3. **筛选后再下载/加工。** 检查作者实际预览、背面/拓扑、时代与风格、许可、依赖、文件大小和手机适用性。优先可合法获取、可编辑、可降面数的成熟资产；不把被登录阻挡的内容算作已获得。
4. **统一后再摆放。** 调整比例、材质、法线、色彩、粗糙度、圆角、服装和光照；避免写实扫描、低模几何与卡通主角直接拼贴。保留源文件、作者、许可、固定版本/hash和优化方法。
5. **代码实现完整空间。** 可使用作者模型与纹理，不要求所有顶点手写；实例化、材质和变体、布置规则、动作、交互、碰撞和镜头保持可编辑。不要用“代码实现”作为拒绝优质外部资产的理由。
6. **看实际画面再决定。** 用同机位/近似构图截图与概念直接比，检查至少人物、建筑体积、场景层次、材质光照、手机可读性。功能通过与美术差距分别记录。
7. **控制真实成本。** 根据运行包大小、显存、绘制调用、近远景面数与实际设备表现做LOD/实例化/距离裁剪；开发源包大小和逻辑物件数量不是浏览器成本或画质结论。不要凭软件渲染推测真机帧率。
8. **及时保存有效成果。** 相关测试通过后重建离线版、提交并推送main，更新当前记录；每轮留下明确下一步，不让新会话重建全部计划。

## 5. 验收：运行正确与看起来完成都要通过

| 验收维度 | 验证方式 | 不能充当通过证据的东西 |
| --- | --- | --- |
| 核心漫游 | 实际操控步行/骑行/飞行、升降/落地、镜头、景点与赏景返回；确认位置和画面状态变化。 | 只有按钮、只有API存在，或直接注入终点。 |
| 城市空间 | 在市集/铺面/宫阶/桥廊/亭台/码头/停泊船实际移动，查看侧后方及空中；水陆边界与可见轮廓一致。 | 仅从一个固定角度截图，或把所有建筑封成不可接近盒子。 |
| 电影美术 | 对照认可参考查看角色、建筑、近景细节、人群、园林、层次、材质、昼夜与镜头；逐项修复明显差距。 | 概念图本身、启动成功、素材数量或“电影档”按钮。 |
| 横屏手机 | 手机尺寸触摸操作、控件点击与遮挡、必要兼容；最终还需对应真机浏览器验收。 | 桌面截图、SwiftShader帧时间或未实际运行的设备推断。 |
| 独立交付 | 最新单HTML重建，加载后断网验证无外部请求，检查源版和包版相关功能、渲染错误与存档回退。 | 旧包、只验证HTTP可下载、声称本地文件已测却无设备证据。 |
| 连续开发 | 代码/素材许可/构建方法/测试证据/实际缺口可从仓库恢复，main远端含有效成果。 | 只有本地提交、易失/tmp记录、只在聊天里记住。 |

用户要求精细打磨直至成熟。仍有明显的概念差距、未实现内容、严重交互问题或未解决兼容风险时，应该继续工作并如实记录；不能为了交差把现状称为全部完成。每次会话的检查点可以提交，但检查点不是最终产品验收。
